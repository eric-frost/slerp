# Slerp architecture

Slerp makes file-manager thumbnails and has a standalone viewer for game and 3D asset files.  One binary, `slerp`, has these commands:

- `slerp thumbnail <size> <input> <output.png>`: run by the freedesktop `.thumbnailer` file.  2D formats decode on the CPU; 3D formats go to the resident helper, or render in-process when it can't be reached.
- `slerp helper`: the resident helper, which keeps a GPU device loaded and serves thumbnail requests over a Unix socket in `$XDG_RUNTIME_DIR/slerp/` (on macOS `$TMPDIR/slerp/`), and the Qt image plugin's requests for pictures and turntables.  On Windows it serves Explorer's thumbnail handler over a named pipe instead, with code from `slerp_shell.dll`.
- `slerp view [file]`: the viewer.  It first hands the file to a warm viewer (one that stayed loaded after its window closed, listening on `$XDG_RUNTIME_DIR/slerp/viewer`), and runs the viewer itself when none listens.
- `slerp render <input> <output.png> [--size N] [--state state.jsonc]`: renders one frame offscreen, for tests and reference images.
- `slerp info <file>`: prints what the file holds.
- `slerp convert <input> <output.glb> [--part P] [--centre] [--png]`: loads any 3D file as the viewer does and writes it as GLB.
- `slerp associate`: which formats get Slerp's thumbnails and open in Slerp by default, applied to the desktop and undone exactly (`--list`, `--thumbnails`, `--default`, `--apply`, `--reset`).
- `slerp formats`: prints the format table, or (`--write`) the files generated from it.

Loaders never depend on each other or on `render`, except `engines`, whose scenes are made of the other loaders' files; the renderer never depends on a loader.  Everything meets in `scene`.

Thumbnails follow one rule, which lives in `core::saved_picture` (`crates/core/src/saved.rs`): when a file carries a picture its authoring program saved of it, file-manager thumbnails show that picture, and only files without one get Slerp's own drawing; the viewer always shows the real content, and its inspector says "Thumbnail: the picture saved in the file".  `carried_picture(kind, path, limits)` has one arm per format that can carry such a picture, each calling a cheap reader in the format's own crate that reads only what the picture needs: Blender's preview (`blend::preview_path`), SketchUp's and 3ds Max's (`previews`), a 3MF package's thumbnail relationship or a slicer project's `Metadata/plate_1.png` and an FBX header thumbnail (`models::saved_picture`), a VRM avatar's portrait (`gltf::saved_picture`), AutoCAD's `THUMBNAILIMAGE` and Rhino's preview (`cad::saved_picture`), slicers' G-code pictures (`paths::saved_picture`), PDF and Illustrator XMP thumbnails and page `/Thumb`s and EPS previews (`documents::saved_picture`), Photoshop's composite and OpenRaster's and Krita's merged pictures (`paint::saved_picture`), an OpenEXR header preview (`images::saved_picture`) and a Litematica schematic's picture (`minecraft::stored_preview`).  `core::prepare_thumbnail` asks it before loading anything, and `slerp render` without `--state` asks it too, so both agree (`--content` draws the content instead).  `saved_picture(kind, path, size)` adds a quality check (`SavedPicture::stands_for_file`), since a poor picture is worse than Slerp's render: one under a quarter of the thumbnail's area (thumbnails counted as 128 to 256 pixels, so a 128 px Blender preview stands at every large size), one flat colour, or one whose subject fills under a tenth of the frame (the box around everything that differs from the colour most of the edge has).  Such a file is drawn, and the poor picture is used only when the content can't be shown.  Formats that are nothing but their saved picture (`Kind::Preview`) load it as their content and don't go through this step, and a material's preview picture stays with the material loader, since the Qt plugin draws materials on a ball regardless.

Some files hold several things shown one at a time, such as a Doom WAD's maps or an LDtk project's levels.  `core::parts(path)` lists them and `core::load_part(path, limits, name)` loads one, while `core::load` keeps giving the whole file (a WAD's gallery of title screen and automaps, which thumbnails show).  The viewer opens such a file on its first part, with a picker for the others, and `ViewState::part` makes `slerp render` draw one.

USD is read by Slerp's own readers (`crates/materials/src/usd/`), not a USD library: `usda` and `usdc` read layers, `stage` composes them, `geom` walks the composed prims into a scene.  `skel` maps UsdSkel onto the scene model: a Skeleton's joints become nodes under its prim's node, the geom bind transform is baked into skinned points so a skin's inverse bind matrices are just the inverted bind transforms, blend shapes (with inbetweens, as extra targets weighted piecewise) become morph targets, and the bound SkelAnimations, their blend shape weights and any time-sampled xformOps become one clip, keyed in seconds by the root layer's time codes per second.  Readers keep every time sample only for those animation attributes, and only when `Limits::animations` asks (thumbnails draw the first sample and bake the first blend shape weights into the points).  `instancer` builds each point instancer prototype once with the same walk, flattens it into meshes and their transforms, and places a node per instance and mesh that shares those meshes; a stage may place 100,000 instances, 400,000 nodes and 100 million copied triangles (a tenth of each for thumbnails), beyond which instancers are thinned evenly with a warning.

Writing glTF is `slerp_gltf::write_glb(scene, selection, options)` (`crates/gltf/src/write/`), used by `slerp convert`, the viewer's File > Save as GLB (`crates/viewer/src/save_glb.rs`, on a thread with a copy of the shown scene) and the Contents panel's exports.  A `Selection` is the whole scene, a node (or several, such as a Blender collection's) with its subtree, one mesh, or one clip with what it moves (or only its skeleton).  `plan.rs` first turns the selection into output nodes: the hierarchy is made a forest, the joints skinned meshes need are added, parents that aren't written fold into the written roots (or into a stand-in parent when a clip moves the node, since clip values are relative to the parent), skinned meshes move to transform-free root nodes and hidden meshes with visible children to hidden child nodes, and skins whose joints have no common root get one; `Placement::Centred` then moves the box to the origin.  The rest repairs what glTF forbids while writing (non-unit normals, unnormalised or duplicate skin weights, indices past the vertices, unequal morph target counts, keyframes out of order) and approximates what glTF can't say (lightmaps as occlusion maps, Doom sprites as crossed quads, splats as points), with warnings, so that the output passes the Khronos validator, which tests check (`tools/validate-gltf.ts`, `tools/glb-sweep.ts`, and `crates/gltf/tests/write_samples.rs` when the validator is installed).  Pictures are written from their original bytes where loaders kept them: `textures::SourceInfo::original` is an `Original::File` byte range (a GLB's embedded image, a neighbouring PNG, free to keep) or `Original::Memory` (data URIs, packed Blender images, FBX, 3MF and USDZ members, kept only when `Limits::originals`, which the viewer sets and thumbnails don't); loaders set it only when the pixels are that picture unchanged.

`core::pages` is the model of documents whose pages the viewer draws again at every zoom: the `Pages` trait (page count, page sizes in the file's units, `draw` of a region into a picture, facts, the word for a page, units per inch for 100 %), with PDF and SVG behind it, and the viewer's `pages_view` on top.  A document of several pages lists them as its parts, so `core::load_part` and `slerp render --state` reach any page.

`core::contents` is the one model of "what is inside a file".  An `Item` has a path that makes a tree, a kind, a size, a detail and the `Format`s it can be saved as (raw, PNG, EXR, WAV, MIDI, GLB, or a map as a WAD; none for things that only mean something inside their file, such as a camera, a blend shape or a rig control, which are listed but never saved or dragged).  Its `Source` is an archive entry, a piece derived from one such as a composite texture, or a `Piece` of what the file's loader produced.  Archives are listed from their own directory (`Contents::open`); every other file is listed by `contents::pieces` from the `Asset` already loaded (`Contents::of_loaded`, which the viewer's loader calls, so listing costs no second load): a scene's nodes as their hierarchy, the collections they are organised in (`Scene::collections`) as folders holding their inner collections and then their nodes (a node or collection in several is listed in each), meshes with their blend shapes, materials, textures (named by their own name in the file, else by the first material slot using them), clips, skeletons, VRM expressions, and a glTF's cameras and lights read from its JSON; a picture's mips, array layers and cube faces, and each cube's six faces as one equirectangular panorama (`contents::panorama`, which reads the faces and lays out the panorama exactly as the renderer's `cube_dir` and `cs_equirect` do, so a saved panorama lights a scene as the cube did; four faces wide, at most 8192 pixels, 4096 for floating point); a canvas's layers, frames and tags; a gallery's pictures; a material file's textures, preview and ball; the file's parts (`core::parts`: an EXR's layers, a PDF's pages, an LDtk project's levels); the picture an authoring program saved in it (`saved_picture`); a MetaHuman's levels of detail and rig controls (`add_character`); and, for zip-based formats (3MF, USDZ, OpenRaster, Krita), the member files under `Files/`, exactly as stored.  Saving takes original bytes first: a texture whose loader kept `SourceInfo::original` (a GLB's embedded PNG, a packed Blender image, an FBX's embedded texture, a picture file beside an OBJ) comes out byte for byte; pictures without one become PNG when 8-bit and OpenEXR (`contents::exr`, uncompressed 32-bit float scan lines) when floating point; scene pieces become GLB through `contents::glb`, the one place that knows `slerp_gltf::write_glb` (a node with its subtree, a collection's nodes, a mesh, a material on a ball, a skeleton from its root joint, a clip with its meshes or the skeleton alone, in place or centred), from the scene the viewer hands over (`Contents::set_scene`, a copy with the file's own visibility) or, without one, the file loaded again once.  `Contents::show` tells the viewer what showing an item means (`Show`: nodes alone, a clip, a blend shape or expression, a surface, a layer, a frame, a tag, a part, a level of detail, or a preview of its own), and `Contents::nodes` which nodes to outline when it is hovered.  `slerp contents list|extract` and the viewer's Contents panel (`crates/viewer/src/contents_view.rs`, a child module of `app`, with the tree widget in `theme`) are both thin over it.  The panel shows pieces in the document already open, setting the document aside (`parked`) only while a piece's own picture is previewed, so returning to the model costs nothing; `contents_view::materialize` writes items to a per-user temporary folder for the clipboard and for drags.  Row pictures (`contents_thumbs.rs`) are made for the rows in view, a few per job on a thread: pictures, mips, layers and frames are shrunk from their pixels (`Contents::thumbnail`), while meshes, nodes and collections are drawn.  `Contents::piece_scene` copies a piece's own geometry out of the scene on screen into a small scene of its own (each mesh a root where the scene puts it at rest, a skinned mesh where its first joint's bind matrix does, with the file's own visibility rather than the viewer's isolation), on the window's thread within a few milliseconds per job, since the viewer's scene lives there; `Contents::draw_piece` draws it off that thread with a `ThumbRenderer::with_gpu` sharing the viewer's GPU, textures shrunk to 128 pixels once each.  Scenes of more than 2,000 meshes or 20,000 nodes, and pieces of more than a million triangles or vertices, get none.

## The format table and the association manager

`crates/formats/src/table.rs` lists every format once.  A format is what a user switches on or off as a whole (Quake and Half-Life `.mdl` are one; so are USD's text, binary and plain layers), with a stable id that saved choices name.  Each MIME type records where it is defined (`data/slerp.xml`, shared-mime-info, or shared-mime-info with Slerp's globs and magic added), so a test can check `data/slerp.xml` against the table both ways: same types, same globs, same aliases.  `data/slerp.xml` itself stays written by hand, because its magic, priorities and glob weights settle clashes between formats sharing an extension (`.map`, `.pal`, `.art`, `.fit`, `.pak`, `.hdr`, `.scn`) and each carries its reasoning; generating it would hide that reasoning in a second language.  Everything else is derived: `generate` writes the thumbnailer's and desktop entry's MIME lists, the macOS app's and Quick Look extension's property lists and the Qt plugin's `slerp.json` and `formats_table.inc`, and a test fails when a checked-in copy differs; the viewer's folder stepping (`viewer_steps_to`), Explorer's extension list (`associate::windows::Selection`) and `core`'s `Kind::format` (the format of a sniffed file, which `crates/core/tests/formats.rs` checks against the test corpus) read the table at run time.

The user's choices (`core::choices`, `file-types.jsonc` beside `config.jsonc`) hold only differences from the table's defaults.  `associate::apply` makes the desktop follow them and records in `associate::Record` (in the state folder, since it describes this machine) what it changed outside Slerp: for files other programs own (`mimeapps.list`, `dolphinrc`), the text before the first change, the text last written and each entry changed, edited line by line through `associate::ini` so nothing else in the file moves.  Applying always starts from the file as it would be without Slerp, so switching a choice off restores its entry, and `reset` writes the original back byte for byte when nobody else has touched the file since, or undoes Slerp's entries one by one when someone has; an entry someone else changed is theirs from then on.  Files Slerp creates (the per-user thumbnailers) record what they replaced.  On Windows the same record holds the thumbnail handlers Slerp replaced, on macOS the default apps.  The macOS and Windows thumbnail handlers, which are registered for every type and can't be told per format, ask `core::choices::thumbnails_wanted` and decline the formats switched off; so does the Qt plugin (`qt/choices.cpp`).

`qt/` isn't a crate: it is the Qt image plugin (C++, CMake), which Qt programs load to read textures as pictures and models as turntable animations.  It runs nothing of Slerp's inside them.  It asks the helper with a `frames > 0` request, which the helper answers with raw frames from `core::prepare_picture` (textures at full size, alpha kept) or `ThumbRenderer::turntable`.  Its client is a C++ copy of `crates/helper`'s, written to the documented wire format so the plugin carries no Rust runtime into every Qt program; a test in the `slerp` crate checks the two agree on the protocol version and limits.

## Platforms

Linux is the primary platform; Windows 11 (x86_64) and macOS (Apple Silicon) run the command line and the viewer.  What differs is gated with `cfg` inside the crate that owns it, so callers stay the same everywhere:

- `render`: Linux picks the GPU from sysfs and the Wayland compositor and pins its Vulkan driver; Windows (Direct3D 12, then Vulkan) and macOS (Metal) turn the policy into wgpu's power preference.  wgpu's `dx12` and `metal` features are enabled per target in `crates/render/Cargo.toml`.
- `helper`: Unix sockets on Linux and macOS (`getpeereid`, `SO_NOSIGPIPE`); on Windows `request` fails at once and `slerp thumbnail` renders in-process, while `slerp helper` loads `slerp_shell.dll` and runs its pipe server.
- `core` and `viewer`: settings, history and caches in each platform's own folders (`core::config::config_dir` and `state_dir`).
- `theme`: KDE and GNOME on Linux; the registry and DWM on Windows; the global preferences on macOS.  Where no icon theme has an icon (always on Windows and macOS), the viewer's icons come from a built-in Lucide set.
- `viewer`: on macOS, files Finder opens arrive as Apple Events, which `src/macos.rs` receives by adding `application:openURLs:` to winit's application delegate.
- `viewer`: items of the Contents panel can be dragged out of the window into a file manager (`dragout`).  winit cannot start a drag out of its windows, so `dragout/payload.rs` holds what is shared (the lazily produced files, safe unique names, `file://` URIs, a private temporary folder, one drag at a time) and each platform adds the window system's call: `wayland.rs` creates a `wl_data_source` on a second event queue of winit's own connection (a thread of its own, and a second `wl_pointer` to learn the serial of the press that starts a drag; X11 sessions return `DragError::Unsupported`), `ole.rs` runs `DoDragDrop` on Windows, and `appkit.rs` begins an `NSDraggingSession` of file promises on macOS.  `tools/test-dragout.sh` tests the Wayland part in a nested sway or KWin with a fake pointer and a drop target (`examples/dragout_testbed.rs`).
- Thumbnails outside Linux: Finder's come from a Quick Look extension inside `Slerp.app`, which calls `crates/macos` (no helper: Quick Look keeps the extension's process, and so its GPU renderer, alive).  Explorer's come from `crates/winshell`'s COM DLL, which Explorer loads into its own process so it gets real paths, and which hands the loading and drawing to the helper process.
- Builds: `tools/build-windows.sh` cross-compiles on Linux (the exe, the shell DLL and the launcher), `tools/build-macos.sh` builds on a Mac over SSH through `tools/macos-app.sh` (which also runs on a Mac directly, with Apple's Command Line Tools and no Xcode); both write to `local/dist/`.

## Packaging

`tools/build-deb.sh` makes the Debian packages.  `slerp` comes from cargo-deb and the `[package.metadata.deb]` table of the root `Cargo.toml`: the binary in `/usr/bin`, the thumbnailer, MIME package, desktop entry and icon under `/usr/share`, and the notices in `/usr/share/doc/slerp/`.  The dpkg triggers of shared-mime-info, desktop-file-utils and hicolor-icon-theme rebuild the caches, so there are no maintainer scripts.  The libraries the program loads at run time (the Vulkan loader, Wayland, xkbcommon, X11) are listed by hand, since dpkg-shlibdeps sees only linked ones.  `slerp-qt-plugin` is put together with dpkg-deb from `packaging/debian/qt-plugin/`, because cargo-deb packages only what Cargo builds, and a package of its own keeps Qt off desktops that don't want it.  `packaging/aur/PKGBUILD` is the same pair as an Arch split package, built from the tarball `tools/source-tarball.sh` makes.  `tools/test-packages.sh` installs either kind in a fresh Ubuntu or Arch container and runs smoke tests and lintian or namcap.  `THIRD-PARTY.md` is generated by `tools/third-party.ts` from `cargo metadata` and the licence files in Cargo's registry, and `docs/formats.md` and the website's `site/formats.json` by `tools/format-list` from the format table.

## Conventions

- Rust 1.93 (Ubuntu 26.04's), edition 2024.  Check a new dependency's `rust-version` before adding it.  egui 0.35 and wgpu 29 are the newest that build with 1.93, and the viewer shares one wgpu device between egui and the renderer, so their versions move together.
- Dependencies must be permissively licensed (MIT, Apache-2.0, BSD, Zlib, ISC, CC0), since Slerp is MIT OR Apache-2.0.
- Coordinates are right-handed, Y up, in metres where the format says what a unit is.  Z-up formats are converted in the loader.
- A loader must never panic or hang on bad input: return `LoadError`, and record recoverable problems (a missing texture file) in `Info::warnings`.  Respect `Limits`.
- A loader lists the files it read (or looked for) beside the main one in `Info::neighbours`, which the viewer watches to reload when one changes.  Loaders that read neighbours on the calling thread note them with `scene::record_neighbour` and wrap their entry point in `scene::collect_neighbours`; glTF, which reads them on worker threads, collects them in its own context.
- Formatting: `rustfmt.toml` (120 columns).  Doc comments explain why, in complete sentences, with two spaces after each period.  Large files are split into regions with the boxed `//region` comments used in `scene/src/lib.rs`.
- Build output goes to `local/target` (`.cargo/config.toml`; `local/` is left out of Git).  Test assets live in `local/assets/`, downloaded by `tools/fetch-test-assets.ts`.
